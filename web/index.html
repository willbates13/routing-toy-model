AOA toy model
Demand Routing Closing the gap Beat the baseline

Every execution, the same boxes get split between two factories.

Customers order boxes. A box is just a vector: how many units of each SKU it needs, with most SKUs at zero. A routing run — an execution — decides which factory picks which box. Between executions customers change their orders, so the demand each factory is planning against keeps moving.

Every execution is a forecast of what each factory will pick, and the last execution is the actual. The factories buy ingredients against the forecast, so if a box hops between sites both of them get it wrong even when the global forecast was fine. That difference is the error this model is about.

Two building blocks

The whole model is two small classes: a box and a factory.

A box is a SKU vector

Each box draws two to four SKUs out of 14, one to nine units of each, and leaves the rest at zero.

A factory hosts some SKUs

A factory adds up the vectors of the boxes it holds, and refuses any box needing a SKU it does not host. Both factories always take the same number of boxes.

Three

Follow one SKU

Pick any SKU with the numbers above the plot. The line is the forecast for it at each execution, and the dashed line is the actual.

A bar above the dashed line means the forecast is over; below means under. The bars close to nothing at the last execution, where forecast and actual are the same thing.

error = forecast − actual

Four

Add up every SKU

Take the size of that error for each SKU, ignoring its direction, add them up and divide by the final global volume. That is a WMAPE — a mean absolute percentage error weighted by volume, so the big SKUs count for more.

global WMAPE = Σk |forecastk − actualk| ÷ Σk actualk

Customer edits and simulated box changes move this line. No routing decision can touch it.

Five

Now split the boxes

The same order volume, divided between two factories. Each takes half the boxes, and a tile outlined in black can only go to factory B.

Scroll on and boxes start hopping sides: that is the optimiser holding its target as customers edit orders and simulated boxes change.

Six

Follow the same SKU into each factory

Three lines now: the global total, and the same SKU at each factory. The two factory lines always add up to the total.

Each has its own dashed finish line, and a bar at every execution showing the distance still to travel.

a = forecast A − actual A  ·  b = forecast B − actual B
a + b = the global error for this SKU

Seven

Do the sum, execution by execution

When both factories forecast the same way — both over their actual, or both under — the split has cost nothing. The global forecast was already that far out.

When one is over and the other under, the two errors cancel in the global total yet both factories are wrong. The numbers under the plot do that sum as you scroll.

sites wrong by = |a| + |b|  ·  global wrong by = |a + b|
the split costs = |a| + |b| − |a + b| = 2 × min(|a|, |b|) when the signs disagree, and nothing when they agree

Eight

Add up every SKU again

Site error is the same WMAPE, but the sizes are taken per factory before they are added up, so the cancelling never happens. The denominator is unchanged, because the two factories' actuals add up to the global actual, which is what makes the two errors directly comparable.

site WMAPE = Σk ( |forecast Ak − actual Ak| + |forecast Bk − actual Bk| ) ÷ Σk actualk

It sits above global error, and the red band between them is that last number on every SKU, added up. Closing the band is the whole game.

factory A factory B global volume added site error
Nine

The condition for no added site error

For one SKU, site error equals global error whenever the two factory errors point in the same direction. They may both be over, both be under, or one may be exactly zero. Then nothing cancels when the factories are added together.

if a and b have the same sign: |a| + |b| = |a + b|
therefore site error = global error

So the design problem is clear: set targets that keep the signs aligned as global order volume changes.

Ten · method one

Hold one site's SKU volume constant

Keep factory A's volume for this SKU fixed and let factory B absorb every change in global volume. A is always on its own actual, so its error is zero. B's error is the entire global error.

In the upper plot, A is the flat blue line while B moves with the purple global line. In the lower plot, site error lies exactly on global error at every execution, so there is no red gap between them.

Af = Aa ⇒ a = 0
b = (Gf − Af) − (Ga − Aa) = Gf − Ga = ΔG
site error = |0| + |ΔG| = |ΔG| = global error

This removes added site error for the SKU by construction.

Eleven · method two

Keep each site's share constant

Alternatively, keep the SKU split proportional at every execution — for example, 40% at factory A and 60% at factory B. Both sites then move with global volume.

In the upper plot, both factory lines rise and fall with the purple global line. In the lower plot, site error and global error overlap again: each site carries the same sign as the global change, so the added site error stays at zero.

a = 0.4ΔG  ·  b = 0.6ΔG
site error = |0.4ΔG| + |0.6ΔG| = |ΔG| = global error

Because both multipliers are non-negative, both errors always take the sign of the same global change. Again, there is no added site error.

Twelve · the physical constraint

But SKUs cannot move independently

A target is written one SKU at a time, but routing moves whole boxes. A box bundles several SKUs together, so moving four units of one SKU can also move two other SKUs that were already on target.

The optimiser has to hunt for a combination of boxes whose bundled contents land close to every SKU target at once. The exact vector may not exist.

Thirteen · eligibility changes the answer

A changed box may lose a route

Suppose a simulated box changes and now contains a SKU that factory A does not host. That whole box becomes ineligible for A, even if its other SKUs would have made it the perfect move.

Customer edits, simulated box changes, equal box-count rules, and site eligibility can therefore make either ideal method impossible in a particular execution.

Fourteen · the optimisation problem

The target is a goal, not a guaranteed split

The optimiser must choose whole, eligible boxes while balancing all SKU targets at the same time. Reaching the mathematical ideal is a non-trivial combinatorial problem, and sometimes the best feasible split still leaves added site error.

That leaves the practical question for the exercise below: given changing order volume, changing box contents, and routing constraints, what is the best way to set the SKU targets?

Beat the baseline

The exact HiGHS optimiser is fixed: equal box counts, eligibility respected, boxes kept whole, and the L1 distance to the target minimised. The only thing you change is how the target is set at each execution. The question is which target rule best survives changing order volume, changing box contents, and the same physical routing constraints.
